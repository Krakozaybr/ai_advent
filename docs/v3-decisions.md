# Решения по v3

Короткий журнал решений, которые влияют на общую основу. Формат: вопрос →
принятое решение → причина.

- Как продолжать ветку от произвольного видимого сообщения Codex? →
  создаётся отдельная Codex thread и получает снимок видимых сообщений через
  `thread/inject_items` перед первым новым запросом → `thread/fork` копирует
  только до заданного завершённого Codex turn (`lastTurnId`), а точка ветки в
  интерфейсе может быть пользовательским сообщением или серединой хода. Такое
  восстановление сохраняет текстовый transcript user/assistant, но не копирует
  скрытое или служебное состояние Codex (системные инструкции, результаты
  инструментов, внутреннее сжатие контекста); UI и API считают источником
  истории ленты её локальный видимый transcript и не обещают тождество скрытого
  prompt context. Если источник уже связан с Codex thread, ветка/клон всё равно
  получает новую независимую thread. Документация: [Codex app-server](https://learn.chatgpt.com/docs/app-server).
- Как обновлять старые файлы досок для происхождения и подготовки контекста? →
  при открытии добавляются недостающие nullable поля происхождения и флаг
  `codex_context_seeded` со значением по умолчанию `true` → существующие ленты,
  сообщения и связи с Codex остаются на месте; только скопированные ленты
  получают флаг повторной загрузки локального снимка. При копировании ответы
  сохраняют run status и ошибку, но получают новые ID.
- Что делать, если `thread/inject_items` завершился таймаутом с неизвестным
  результатом? → забыть ID этой новой Codex thread и на повторе создать другую,
  заново загрузив сохранённый локальный transcript → повторная инъекция в ту же
  thread могла бы продублировать историю, если сервер выполнил запрос, но ответ
  потерялся.
- Как не сорвать параллельные первые запросы разных лент? → удерживать mutex
  старта Codex app-server до завершения `initialize` → ожидание только общей
  первичной инициализации; сами Codex threads выполняются параллельно.
- Где хранить новые доски, не затрагивая первую SQLite-базу? → исходный
  `v3/data/board.sqlite` остаётся первой доской, новые базы создаются как
  отдельные файлы в `v3/data/boards/` → миграция не копирует и не удаляет
  существующую историю.
- Где сохранять выбранную вкладку? → в `localStorage` браузера; сервер отдаёт
  список досок и выбранную доску по её ID → выбор локален для пользовательского
  интерфейса, а содержимое и запросы остаются серверными.
- Какие операции с настройками провайдера доступны сейчас? → провайдер
  закрепляется при создании ленты и дальше не меняется; выбор провайдера,
  модели и параметров доступен для новых лент и запросов.
- Как должны работать правка и удаление сообщений? → действие применяется к
  выбранному сообщению и всему хвосту только исходной ленты; UI предупреждает
  об удалении хвоста и сообщает, что существующие ветки/клоны остаются
  неизменными, включая снимок текста точки ветвления в подписи происхождения.
  Операция и проверка активного запроса выполняются в одной
  SQLite-транзакции. Привязка ленты к Codex thread сбрасывается, следующий
  запрос начинает новую thread из точной сохранённой видимой истории → старый
  удалённый/отредактированный контекст больше не просачивается через прежнюю
  server-side thread.
- Где разрешено копировать блок? → в любую другую неактивную ленту той же
  доски; источник тоже должен быть неактивен. Иная доска не предлагается в
  выборе, потому что блок переносит контекст провайдера вместе с общей историей
  только в пределах одной доски. Копируется роль и текст с новым message ID;
  целевая привязка Codex thread сбрасывается и история будет восстановлена из
  видимого transcript → цель явно не продолжает старую thread с разорванным
  контекстом.
- Как отображать Markdown в блоках? → один React-компонент используется для
  сохранённого и поступающего текста, с GFM, LaTeX и подсветкой fenced code;
  исходный HTML выключен, KaTeX trust выключен, ссылки проходят стандартную
  безопасную обработку react-markdown → содержимое модели не исполняется как
  разметка браузера. Внутренние рассуждения не запрашиваются и не отображаются.
- Как раскладывать ленты на доске? → координаты X/Y и ширина хранятся в SQLite
  для каждой ленты; заголовок перемещает карточку по бесконечной прокручиваемой
  рабочей области, боковой маркер меняет ширину. Режим «Фокус» центрирует
  выбранную карточку прокруткой, не меняя её сохранённые координаты; положение
  режима и выбранная лента остаются локальным предпочтением интерфейса. Старые
  ленты при открытии получают отдельные соседние координаты; новая ветка/копия
  добавляется рядом с остальными → вид доски не превращается в последовательную
  страницу и при миграции карточки не перекрывают друг друга.

## Импорт подготовленных досок

- Как загружать готовое содержимое доски? → общий `POST /api/boards/import`
  принимает стабильный `externalId`, заголовок, ленты, безопасные настройки,
  сообщения, layout, ссылки ветвления и отдельные записи агентов → протокол не
  содержит учебных дней и шаблонов; JSON-пакеты и CLI находятся вне
  backend/frontend.
- Как повторный импорт соотносится с пользовательской историей? → первый импорт
  создаёт отдельную SQLite-базу через временный файл, фиксирует сущности в
  транзакции и атомарно переносит файл в каталог досок; повторный
  `externalId` возвращает существующую доску без обновления полей и истории.
  API не принимает целевой `boardId`.
- Какие значения запрещены? → ограничены размер запроса, число лент/агентов,
  число и размер сообщений, роли только `user`/`assistant`, диапазоны config и
  layout; поля секретов и provider thread IDs отклоняются до записи.
- Как показывать заготовленные ответы? → provenance хранится у сообщения и
  показывается рядом в интерфейсе. Seed-примеры маркируют демонстрационные
  ответы; при первом запросе импортированная история остаётся transcript и
  загружается Codex либо попадает в общий план OpenRouter.
- Как представить учебного агента? → агент — отдельная запись SQLite с
  названием, описанием и инструкциями; лента может ссылаться на неё. UI
  показывает сохранённую сущность и связь, а не подменяет её кнопкой отправки.

Сценарии дней 1–9 находятся в `examples/ai-advent/`; platform-код не зависит
от этой директории и не распознаёт значения её `externalId`.

## Этап v3: провайдеры и настройки

- `provider` назначается при создании ленты и не меняется через API; старые
  ленты при миграции получают `codex`, а ветка и клон копируют провайдера и
  настройки источника.
- OpenRouter использует серверный ключ `data/openrouter.key` с правами только
  владельца, потоковый Chat Completions API и параметры `model`, `temperature`,
  `max_tokens`, `stop`. В v2 ключ лежит в `data/settings.json` с такими же
  правами; браузер не получает его.
- Codex показывает выбор из `model/list` и передаёт `model` в `turn/start`;
  локальная схема app-server подтверждает поддержку обоих полей. Temperature,
  max tokens и stop для Codex не отображаются и не передаются.
- Модель и поддерживаемые значения задаются в настройках каждой ленты и могут
  переопределяться в запросе. SQLite хранит снимок конфигурации запуска и
  технические данные ответа: фактическую модель, статус HTTP, длительность,
  usage и finish reason, если провайдер их прислал. Секреты не сохраняются.
  Ключ OpenRouter общий для локального приложения и доступен лентам всех досок.
- Дефолты: Codex оставляет модель по умолчанию app-server, OpenRouter начинает
  с `openai/gpt-4o-mini`, temperature `0.7`, max tokens `2048`, без stop.
- OpenRouter отменяется вместе с coroutine и HTTP-потоком. Codex получает
  `turn/interrupt` с thread/turn ID, когда app-server вернул активный turn;
  локальная история помечает запрос как `cancelled`.

За пределами этого этапа остаются общие значения по умолчанию на уровне всего
приложения, реестр моделей OpenRouter и расширенные параметры сверх temperature,
max tokens и stop. Текущий контракт хранит параметры в ленте и снимок в запросе.

## Контекст дней 8–9 — общее решение для досок и провайдеров

- Полный transcript живёт в локальной SQLite истории сообщений и никогда не
  сокращается автоматически. План отправки строится отдельно и действует для
  любой ленты/доски и для обоих провайдеров: `full`, `sliding_window` последних
  N сообщений или `summary_window` (отдельная сводка + последние N сообщений).
- Сводка хранится в полях ленты вместе с ID последнего сообщения, учтённого при
  её создании (`watermark`). Пользователь создаёт и обновляет сводку отдельной
  явной кнопкой. До тех пор, пока transcript изменяется, UI помечает сводку как
  устаревшую; она не обновляется и не выбрасывается незаметно. Создание сводки
  отправляет провайдеру полный transcript в отдельном вызове; ответ сохраняется
  отдельно и не добавляется в диалог. Codex использует ephemeral thread.
  При правке или удалении transcript сохраняется текст summary и watermark,
  но выставляется отдельный признак устаревания.
- Генерация summary снимает fingerprint упорядоченного transcript (ID, роль,
  текст) до вызова модели и сравнивает его с текущими данными в транзакции
  сохранения. Несовпадение даёт конфликт и не публикует поздний результат;
  короткий compare-and-save не удерживает блокировку во время LLM-вызова.
- При каждом запросе сохраняется точный выбранный план вместе со снимком
  параметров. UI показывает сообщение пользователя, выбранные сообщения и
  оценку токенов сообщения, истории и ответа; оценка считается по длине текста
  (примерно 4 символа на токен) и явно не называется фактическим токен-счётом.
  Фактические данные ответа показываются отдельно: OpenRouter передаёт
  `stream_options.include_usage=true`; Codex использует последнее событие
  `thread/tokenUsage/updated`, только если оно действительно пришло.
- Ограниченные стратегии Codex каждый раз создают ephemeral thread и загружают
  в неё точный выбранный план. Они не продолжают существующий persistent thread
  и не сохраняют ephemeral ID как состояние ленты. Стратегия `full` сохраняет
  прежний persistent thread. Это исключает скрытое продолжение сообщений,
  опущенных только в UI.
- Бюджет — явная оценка пользователя, а не заявление о лимите конкретной
  модели. При превышении UI показывает состав и предупреждение; запрос разрешён
  после явного «отправить всё равно». Сервер повторно вычисляет оценку,
  отклоняет запрос без подтверждения до записи сообщения и сохраняет ошибки
  провайдера вместе с уже сохранёнными user/assistant сообщениями при force-send.
- Миграция добавляет настройки стратегии, N, бюджет, summary и watermark к
  существующим лентам; по умолчанию старые ленты получают `full`. Сообщения и
  существующие связи persistent Codex threads не перезаписываются.
- При ветвлении и клонировании наследуются выбранная стратегия, N и бюджет.
  Summary не копируется: у ветки может быть отсечён transcript до её watermark,
  поэтому новую сводку нужно явно построить по новой истории.

## Ближайший законченный срез и критерии

1. Серверная история/копирование: API редактирования, удаления-хвоста,
   переноса блока и сохранения layout; тесты проверяют активный конфликт,
   хвост, независимые snapshots ветки/клона, сброс Codex ID и точный context
   seed, новые IDs и недопустимые цели.
2. Markdown в интерфейсе и действия над сообщениями: один безопасный renderer
   для завершённого и потокового текста, копирование текста, подтверждение
   разрушающих правок, перенос в другую ленту; frontend tests/build.
3. Доска: перетаскивание и изменение ширины с серверным сохранением, режим
   фокуса с центрированием карточки, не меняющий геометрию; ручной осмотр с
   временной БД, если локальный Codex вход доступен.

Готовность: `./gradlew test` из `v3/backend`, `npm test` и `npm run build` из
`v3/frontend`, корневые `npm test`/`npm run build`, `git diff --check`; ручной
сценарий отмечается отдельно от автоматических проверок. Работа остаётся
локальной, разбивается на небольшие коммиты, без push и без доступа к
пользовательской SQLite-БД для тестовых данных.
