# Решения по v3

Короткий журнал решений, которые влияют на общую основу. Формат: вопрос →
принятое решение → причина.

- Как продолжать ветку от произвольного видимого сообщения Codex? →
  создаётся отдельная Codex thread и получает снимок видимых сообщений через
  `thread/inject_items` перед первым новым запросом → `thread/fork` копирует
  только до заданного завершённого Codex turn (`lastTurnId`), а точка ветки в
  интерфейсе может быть пользовательским сообщением или серединой хода. Такое
  восстановление сохраняет текстовый transcript user/assistant, но не копирует
  скрытое или служебное состояние Codex (системные инструкции, результаты
  инструментов, внутреннее сжатие контекста); UI и API считают источником
  истории ленты её локальный видимый transcript и не обещают тождество скрытого
  prompt context. Если источник уже связан с Codex thread, ветка/клон всё равно
  получает новую независимую thread. Документация: [Codex app-server](https://learn.chatgpt.com/docs/app-server).
- Как обновлять старые файлы досок для происхождения и подготовки контекста? →
  при открытии добавляются недостающие nullable поля происхождения и флаг
  `codex_context_seeded` со значением по умолчанию `true` → существующие ленты,
  сообщения и связи с Codex остаются на месте; только скопированные ленты
  получают флаг повторной загрузки локального снимка. При копировании ответы
  сохраняют run status и ошибку, но получают новые ID.
- Что делать, если `thread/inject_items` завершился таймаутом с неизвестным
  результатом? → забыть ID этой новой Codex thread и на повторе создать другую,
  заново загрузив сохранённый локальный transcript → повторная инъекция в ту же
  thread могла бы продублировать историю, если сервер выполнил запрос, но ответ
  потерялся.
- Как не сорвать параллельные первые запросы разных лент? → удерживать mutex
  старта Codex app-server до завершения `initialize` → ожидание только общей
  первичной инициализации; сами Codex threads выполняются параллельно.
- Где хранить новые доски, не затрагивая первую SQLite-базу? → исходный
  `v3/data/board.sqlite` остаётся первой доской, новые базы создаются как
  отдельные файлы в `v3/data/boards/` → миграция не копирует и не удаляет
  существующую историю.
- Где сохранять выбранную вкладку? → в `localStorage` браузера; сервер отдаёт
  список досок и выбранную доску по её ID → выбор локален для пользовательского
  интерфейса, а содержимое и запросы остаются серверными.
- Какие операции с настройками провайдера доступны сейчас? → выбора и смены
  провайдера нет, текущий путь Codex фиксирован → пользователь отложил
  конфигурацию до отдельной итерации и запретил переход провайдера в ленте.
- Как должны работать правка и удаление сообщений? → действие применяется к
  выбранному сообщению и всему хвосту только исходной ленты; UI предупреждает
  об удалении хвоста и сообщает, что существующие ветки/клоны остаются
  неизменными, включая снимок текста точки ветвления в подписи происхождения.
  Операция и проверка активного запроса выполняются в одной
  SQLite-транзакции. Привязка ленты к Codex thread сбрасывается, следующий
  запрос начинает новую thread из точной сохранённой видимой истории → старый
  удалённый/отредактированный контекст больше не просачивается через прежнюю
  server-side thread.
- Где разрешено копировать блок? → в любую другую неактивную ленту той же
  доски; источник тоже должен быть неактивен. Иная доска не предлагается в
  выборе, потому что блок переносит контекст провайдера вместе с общей историей
  только в пределах одной доски. Копируется роль и текст с новым message ID;
  целевая привязка Codex thread сбрасывается и история будет восстановлена из
  видимого transcript → цель явно не продолжает старую thread с разорванным
  контекстом.
- Как отображать Markdown в блоках? → один React-компонент используется для
  сохранённого и поступающего текста, с GFM, LaTeX и подсветкой fenced code;
  исходный HTML выключен, KaTeX trust выключен, ссылки проходят стандартную
  безопасную обработку react-markdown → содержимое модели не исполняется как
  разметка браузера. Внутренние рассуждения не запрашиваются и не отображаются.
- Как раскладывать ленты на доске? → координаты X/Y и ширина хранятся в SQLite
  для каждой ленты; заголовок перемещает карточку по бесконечной прокручиваемой
  рабочей области, боковой маркер меняет ширину. Режим «Фокус» центрирует
  выбранную карточку прокруткой, не меняя её сохранённые координаты; положение
  режима и выбранная лента остаются локальным предпочтением интерфейса. Старые
  ленты при открытии получают отдельные соседние координаты; новая ветка/копия
  добавляется рядом с остальными → вид доски не превращается в последовательную
  страницу и при миграции карточки не перекрывают друг друга.

## Ближайший законченный срез и критерии

1. Серверная история/копирование: API редактирования, удаления-хвоста,
   переноса блока и сохранения layout; тесты проверяют активный конфликт,
   хвост, независимые snapshots ветки/клона, сброс Codex ID и точный context
   seed, новые IDs и недопустимые цели.
2. Markdown в интерфейсе и действия над сообщениями: один безопасный renderer
   для завершённого и потокового текста, копирование текста, подтверждение
   разрушающих правок, перенос в другую ленту; frontend tests/build.
3. Доска: перетаскивание и изменение ширины с серверным сохранением, режим
   фокуса с центрированием карточки, не меняющий геометрию; ручной осмотр с
   временной БД, если локальный Codex вход доступен.

Готовность: `./gradlew test` из `v3/backend`, `npm test` и `npm run build` из
`v3/frontend`, корневые `npm test`/`npm run build`, `git diff --check`; ручной
сценарий отмечается отдельно от автоматических проверок. Работа остаётся
локальной, разбивается на небольшие коммиты, без push и без доступа к
пользовательской SQLite-БД для тестовых данных.
